# Plan 05 - Configuration and deployment: a local `.env` now, Cloud Run later

**Status:** plan only, 2 Oct 2026. Decided by the user the same day: develop and test with the user's own bucket and the `yaroslav` namespace; keep every environment variable, every Kubernetes connection value and the bucket name in a local `.env`; later deploy to Cloud Run, which will run against a different bucket and a different Kubernetes cluster (being created for this project) with the settings supplied as Cloud Run variables.

Evidence convention: **[V]** verified when this was written; **[C]** derived from verified facts; **[U]** general platform behaviour not verified here, to check at deploy time.

## 1. The principle

The code never names a cluster, namespace, pool, bucket or image. Every such value is a **setting**; the local `.env` is just one way to supply settings, and Cloud Run's environment variables are another. The same code, unchanged, runs in both places. Three consequences follow.

- **One loader, one precedence:** process environment variable, then `.env`, then the built-in default. A deployed service sets environment variables and has no `.env`; a laptop has a `.env` and usually sets nothing.
- **No target-specific constants.** The pool allow-list, the namespace allow-list and the context guard are settings (doc 01 section 5.11). The convention verified on today's cluster (`<namespace>-{worker,power}-node-pool`) is a value in `.env`, not a rule in code, because the new cluster may name its pools differently.
- **Wrong-target protection is explicit.** At startup `kubejobs` prints a banner naming the cluster, namespace and bucket it will act on, validates every setting, and refuses to run if the active kube context does not match `KUBEJOBS_KUBE_CONTEXT`.

## 2. Settings reference

All names are prefixed `KUBEJOBS_` (the UI package `controlplane` has a few of its own, marked `CONTROLPLANE_`). A setting is added to the code together with the feature that reads it, so some rows below (`AUTH`, `K8S_ENDPOINT`, `K8S_CA_CERT`, `HISTORY_*`, `CONFIRM_COST_USD`, the UI bind address) describe the plan and are not yet in `kubejobs/settings.py`. The local file is `.env` at the repository root; it already exists on the user's machine with the v1 values below. It holds **no credentials**: Kubernetes access comes from the user's gcloud login (`gke-gcloud-auth-plugin` [V working]), and the source-API keys stay in the pods' own Secret, never here.

Two details about sharing the `.env` with the pipeline:

- **It can be one file.** `jdluc/config.py` reads only its own six fields from the `.env` it finds and ignores everything else [V from source], so the pipeline's `INGEST_ROOT`, `SCRATCH_ROOT` and so on can sit in the same file as the `KUBEJOBS_` keys. `kubejobs` never requires the pipeline's keys. With the approved environment-first change (issue #8 proposal 17) those six fields can also come from process environment variables, which is how a Cloud Run service supplies them. (Environment variables overriding those six fields was dropped in review on 5 Oct: they are read from the file only.)
- **The pods' `.env` is a different file.** What a pod reads is the Secret mounted at `/app/.env`, created from `infra/cloud.env` (kept out of git by the `infra/*.env` rule [V]). Deriving that file from the same settings, so the bucket name exists in one place, is a later convenience (`kubejobs secrets render`, not in v1); creating the Secrets stays a manual, explicit step.

Safety already in place \[V\]: `.env`, `infra/*.env` and `.cache/` are in `.gitignore`, and `.dockerignore` excludes `.env` and `**/*.env`, so none of it reaches git or an image.

## 3. Day-to-day, locally

1. `.env` exists (the v1 values above). The tracked `.env.example` gains a `KUBEJOBS_` section listing every setting with a placeholder, so a new machine or the Cloud Run configuration starts from the same list.
2. `uv run python -m kubejobs doctor` validates the settings and the access they imply, read-only: required settings present, kube context matches, namespace exists, the Secrets and KSA exist, the image resolves to a digest, the bucket is writable at the history prefix, Cloud Logging is readable, and the pipeline's capabilities (which tile sizes it supports; doc 06 section 3.1). It prints the target banner. Every other command runs the same checks first.
3. `uv run python -m kubejobs submit ...`, `... status`, and `uv run --group ui python -m controlplane` (the UI) all read the same `KUBEJOBS_` settings.

## 5. Migration checklist for the new cluster and bucket

Done from the laptop first, with a second env file (`.env.new`, selected by pointing `KUBEJOBS_ENV_FILE` at it), so nothing is discovered for the first time in production.

1. New bucket and prefix; the `cornerstone/` layout is created by the first run.
2. New namespace, the pods' KSA with its Workload Identity binding, the two Secrets, the registry path for the image.
3. Node pools matching the two roles (heavy and light), tainted the way `manifest.py` tolerates, plus the shared pool if one is wanted.
4. Namespace Role and optional ClusterRole from doc 01 section 5.13, bound to the Cloud Run service account.
5. IAM for that service account: object access on the bucket prefix, `logging.viewer`, `monitoring.viewer`, `container.clusterViewer` if the endpoint is looked up.
6. `kubejobs doctor` against the new target from the laptop; then one single-tile run end to end.
7. Deploy the service with the same settings as environment variables; run `doctor` through the service; repeat the single-tile run through the UI.

## 6. Risks and open items

- **Cloud Run to cluster networking** is the main unknown and cannot be tested until the new cluster exists. Ask whoever builds it which endpoint type it will have.
- **IAM administration:** every service-account grant above needs project IAM admin, which the user lacks (`getIamPolicy` is denied [V]); it is a request to whoever administers the project.
- **Drift between `.env` and Cloud Run variables:** mitigated by the single `.env.example`, startup validation, and the banner.
- **The pods' Secret still holds the bucket name separately** until `secrets render` exists; changing buckets means updating both.
- Nothing in this document has been run against Cloud Run; the Cloud Run behaviours marked [U] need checking against current documentation when the deployment step starts.
